# 失败归因在检测流水线内聚合，按阶段与订阅备注两个维度计数

**Status**: accepted

测活、解锁检测、名称筛选、测速四个阶段各在流水线内部把丢弃的节点按五类失败原因（超时、连接失败、TLS 失败、被筛选、测速不达标）累加，并按节点的订阅备注再做一层计数，随 `/api/status` 一起返回。这样概览页能回答"两万多个节点为什么只剩 6 个"，以及"哪个订阅在拖后腿"——这两问正是日志完全无法回答的部分，也是用户"看不懂"的根因。

## Considered Options

- **前端解析日志**：不用改后端，但日志格式一变就静默失效，且无法在 2 万条记录的规模上做实时聚合。
- **把每个失败节点写入结果快照**：能钻到单节点，但一轮两万多条失败记录，体积与传输成本都要重新设计，而失败节点本来就注定被丢弃，明细价值低。
- **流水线内聚合**（选中）：常量级内存（一张失败原因表 + 一张按订阅的表），前端只拿汇总数字。

## Consequences

- 计数必须守恒：每阶段 存活 + 各类失败 = 该阶段输入，这一条要由测试保护，否则漏斗会出现"加起来不等于总数"的经典错误。
- 归因的计数口径由后端定义，前端只负责画；概览页不做二次推导。
- 失败原因从五类扩展时，要同时改流水线计数、`/api/status` 形状与概览页文案，三处共用 `GLOSSARY.md` 里的词汇。
- 概览页的"上一次用了 14 分钟"来自结果快照的耗时字段，与归因无关，不要在归因数据里重复记录耗时。
